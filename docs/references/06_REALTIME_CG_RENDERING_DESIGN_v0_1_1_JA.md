## 0. 結論と仕様状態

**PC向けHDRPで、通常の3D環境の中に「真の4D形状から生成した3D断面メッシュ」を置き、通常のPBR照明系で描画する構成を推奨する。**

初期方式は、面取りした凸な木製駒と盤を有限の第4軸方向へ押し出した形状とし、CPUの半空間交差によって閉じた3D断面を作る。GPU Computeは最初の必須条件ではなく、計測後の最適化候補とする。見た目の品質は、正しい輪郭・面取り、木目と粗さ、照明・反射、カメラの組合せで作り、全面的なレイトレーシングを前提にしない。

| 状態 | 内容 |
|---|---|
| 確定 | 今回のユーザー要求：美しい屋外広場、木製盤・駒、真の4D断面、PC先行、人物なし、起動時UIなし、実装しない |
| 提案 | HDRP、別PC表示プロジェクト、凸体押し出し、CPU断面生成、材質場、1440p/60fps目標、下記検証工程 |
| 検証待ち | 対象局面での大部分の駒の消失、90度断面の外観、時間方向の安定性、Unityパス間整合、GPU/CPU性能 |
| 未決定 | 正確なUnity・パッケージ版、w方向寸法、停止角、Scene 05の合法な着手列、補助残像の扱い、素材予算 |

以後の具体方式と数値は、別記がなければ提案である。解析上の成立と実機での品質・性能を同一視しない。

## 2. 全体アーキテクチャ

| 層 | 所有するデータ・責務 | 所有しないもの |
|---|---|---|
| RuleCore | N次元整数座標、手番、駒ID、合法手、王手・終局、ルール版、遮蔽方式 | Unity、画面可視性、カメラ、材質 |
| ScenarioController | 承認された着手列、再生時刻、演出の順序、CPU応答待ち | 合法性の独自判定、断面に合わせた局面改変 |
| PresentationSnapshot | 局面版、駒ID、表示用の4D補間姿勢、形状版 | ゲーム状態への書込み |
| SliceGeometryCore | 4D形状、観察超平面、交差、断面の頂点・面、幾何可視性 | 照明、Bloom、ゲーム上の攻撃遮蔽 |
| UnityGeometryAdapter | 軸・単位変換、Meshへの転送、bounds、描画パスへの接続 | ルールの変更 |
| Rendering | HDRP/URP、PBR、影、GI、反射、AA、ポスト処理 | 不都合な駒を任意に隠す処理 |
| Cinematic/VFX | 3Dカメラ、時間的履歴、音と光の演出、任意の注釈 | 現在の実体座標の偽装 |

データの基本方向は、RuleCore → Snapshot → 4D形状配置 → 超平面交差 → 3D断面メッシュ → 描画。カメラ操作と断面操作からRuleCoreへの書込みはない。

**GameStateの整数座標、駒の表示用移動補間、観察超平面、通常の3Dカメラを別変数・別更新系にする。** 観察断面が変わっても局面ハッシュ、合法手、CPUの入力集合は変化しない。

一つの描画フレームは同じSnapshot版とSlice版を使用する。カラーだけ新断面、影だけ旧断面、といった混在を防ぐ。断面外の駒はルールから消さないが、断面空間の色・深度・影・反射の実体集合からは除く。

### 2.1 「2Dから4Dへ」と対局ルールの固定

Scene 01を通常将棋のように見せることと、本将棋互換のN=2対局を実行していることは別である。Showcaseを一続きの対局として再生するなら、開始時から固定した4Dルールと局面を使い、最初はv=w=0付近の配置を通常盤の構図で見せる案。画面が広がるたびにルール次元や遮蔽方式を変更しない。

本物のN=2標準対局から異なるルールへ移る構成を選ぶなら、別対局または明示的なシナリオ区間として扱う。N=2の互換性試験に高次元への逃走を混ぜない。この区分は起動時にメニューを表示する要件ではなく、シナリオ定義と記録の契約である。

### 2.2 背景と4D物体の境界

推奨は、広場・テーブル・花瓶・噴水を通常の3D環境として保ち、盤・駒・意味のある盤領域だけを4D形状として切る構成。

これは「4Dの広場全体の光伝播を計算する」方式ではない。**4Dの幾何を正しく切り、その結果を3D空間の光学モデルで照らす**。照明規約を明示することで、幾何学的厳密性とリアルタイムPBRを両立させる。

断面内の座標系はテーブル中央に固定した表示アンカーへ置く。垂直を保つ断面回転を初期候補とし、盤がテーブルへ突き刺さったり、大きくはみ出したりしないかを全経路で調べる。都合の悪い瞬間だけ形状を縮めたり、4D座標をずらしたりしない。

## 3. レンダリング基盤の比較と推奨

### 3.1 HDRP / URP

| 構成 | この用途での利点 | 注意点 | 推奨位置 |
|---|---|---|---|
| HDRP / Deferred中心 | 高画質の材質・反射・ボリューム・RT機能を統合しやすい | GBufferや高度効果の負荷。断面メッシュの各パス整合が必要 | **PC本命** |
| HDRP / Forward中心 | 小物中心の少数光源シーンで比較する価値がある | MSAAとの組合せではSSR・RT等の制約がある | PC比較用 |
| URP / Forward | 将来の単体Quest用に絞った設計をしやすい | PCでHDRP相当の効果を求めると個別開発が増える | **Quest本命** |
| URP / Forward+ | 動的光源が増えた場合の比較候補 | 少数光源なら必ず有利とは限らない | Quest比較用 |
| 共通の一つの描画構成 | 管理が一見簡単 | PCの画質またはQuestの負荷に妥協しやすい | 今回は非推奨 |

Unity 6.3の機能比較では、WindowsはHDRP/URPに対応する一方、Android・モバイルVRはHDRPの対応対象ではない。HDRPには標準のSSR・スクリーンスペースGI・レイトレース反射等がある。[W01]

HDRPのDeferredは不透明物の第一候補とし、半透明の格子・水・VFXは対応するForwardパスへ分ける。「Deferredだから速い」とは扱わない。主光が太陽一本中心のシーンでもあり、同じ品質のForward構成と実測比較する。HDRP 17.0資料では、MSAAはForwardのみで、SSRやRT等に併用制約がある。[W03]

### 3.2 PCの描画プロファイル

| プロファイル | 用途 | 内容 |
|---|---|---|
| GeometryReference | 幾何の正しさ・時間的破綻の検査 | ネイティブ解像度、SMAA、RTなし、DOF/ブラーなし、固定露出 |
| ShowcaseRaster | 最初の高品質な実時間版 | PBR、静的背景GI、動的断面へのプローブ照明、シャドウ、反射プローブ、SSR、穏やかなDOF |
| ShowcaseRT | 追加品質比較 | 動的形状のRT登録を確認後、反射等を一つずつ比較。RTGIは別GI構成として比較 |
| ReferencePathTrace | 静止した材質・照明の比較画像 | 収束させた参考画像。実時間FPSの成果に数えない |

HDRPのRT利用はWindows/DX12を前提に、ドライバー、対応判定、パス設定を確認する。GPUの型番だけで動作成立を認定しない。[W04]

HDRPのパストレーサーはサンプルを蓄積してノイズを減らし、カメラ移動で蓄積を再開する。初期デモの連続4D変形と映画的移動を、パストレースの収束画像と同じ品質で60fps描けるとは約束しない。[W05]

### 3.3 Unityとパッケージ

**Unity 6.3 LTS系を基準候補にし、試験したパッチへ固定する案。** 公式の通常サポート期限は2027年12月。新しいUpdate版を一律に不安定とみなすのではなく、この案件では再現可能な比較と版固定を優先する。[W02]

既存プロジェクトの現行 `ProjectVersion.txt` とパッケージ一覧は本チャットで直接監査していない。既存M0をHDRPへ変換せず、新しいPC表示プロジェクトを設け、共通パッケージ参照で分離する案を00へ返す。

| 用途 | 候補と版固定方針 |
|---|---|
| 描画 | 選んだEditorに適合するHDRP、SRP Core、Shader Graphを組として固定 |
| 幾何高速化 | Unity adapter側でJobs/Burst/Collectionsを検討。Unity非依存の参照数学は維持 |
| カメラ・順序制御 | Cinemachine / Timelineを候補。物体の4D座標やルールの正本にはしない |
| エフェクト | VFX Graphまたは小規模なParticle System。内容に応じて選ぶ |
| 計測・収録 | Profiler、Memory Profiler等。収録は実時間計測と分離 |
| 将来XR | Quest用URPプロジェクト側でOpenXRと必要なMeta連携を適合版へ固定 |

`manifest` とlockファイルへ実際に解決された版を保存する。下記で参照するHDRP 17.0の個別資料は機能・制約の確認根拠であり、将来採用するパッケージの正確な版・APIの保証ではない。最新の別系統のマニュアルを混ぜて同一構成が成立するとみなさない。

## 4. フォトリアル環境と照明

### 4.1 材質

| 対象 | 推奨表現 | 再現の限界・代替 |
|---|---|---|
| 将棋盤 | 実形状の縁の面取り、木目の方向性、粗さの弱い変化、細い正確な盤線 | AI画像の線や傷をそのまま貼らない |
| 将棋駒 | 駒種ごとの微妙な寸法差、面取り、木肌、黒い文字材、接地する影 | 初期の細かい彫刻はnormal/heightの光学近似。真の凹形状は別段階 |
| テーブル・箱 | 暗い木色、広い反射と細かい木目、必要なら薄い仕上げ層 | 全面鏡面や過剰な濡れ表現を避ける |
| 石材 | スキャン由来PBR、実寸の凹凸、目地、近景のみ形状変位 | 遠景の微細凹凸はnormalへ落とす |
| 金属 | 非金属と区別した反射色・粗さ、必要な小物だけ | 木を金属パラメーターで光らせない |
| ガラス・水 | 薄い窓と厚い透明体を区別。水面の流動normal、反射、少量の屈折 | 全面の高負荷な屈折や流体計算を必須にしない |

Base Color、Normal、Roughness/Smoothness、必要に応じてAO・Height・仕上げマスク・文字マスクを用意する。色とデータの色空間を区別し、マップのチャンネル構成は採用パイプラインに合わせて変換する。HDRP Lit / Lit Shader Graphを材質の基礎とし、最初から独自の照明モデル一式を作らない。[W06]

作業用テクスチャ候補は、主役の盤・卓に4K級、駒に共有2K級＋近接用の細部、背景に1K〜2K級。これは固定要件ではなく、画面上の大きさとVRAM測定で決める。全素材8Kを初期条件にしない。頂点数を増やすより先に、輪郭、粗さ、陰影、実寸感を整える。

### 4.2 GI・反射の構成

**静的GI版を基準とし、リアルタイムGI版は別構成で評価する。全部を加算してONにする設計にはしない。**

| 項目 | 基準案 | 検証・注意 |
|---|---|---|
| 静的GI | 広場・建築・固定卓にベイク。動く盤・駒を固定の影として焼き込まない | 高次元動作後に古い影が残らないこと |
| 動的物体の間接光 | APVなどから生成済み3D表面の位置で受光 | ベイク済み照明を参照する方式であり、駒移動による多重反射を再計算するものではない |
| SSGI | 別GIプロファイルとして比較 | 画面情報・履歴への依存、既存GIとの置換・fallback条件を版ごとに検証 |
| RTGI | 後段の品質比較 | 加速構造更新、ノイズ、動的トポロジー、実フレーム時間 |
| Reflection Probes | 静的環境の反射基盤。卓付近の局所配置 | 動く駒を静的キューブマップへ焼き込まない |
| SSR | 卓・盤の反射へ限定して強度調整 | 画面外のものを扱う制約、消失駒の履歴 |
| RT反射 | SSRとの差が重要なカットで比較 | 切断前の元メッシュを反射しないこと |
| 平面反射 | 水面が主要カットで必要な場合のみ | 追加ビューの描画費用に見合うか測定 |

APVはベイクした間接照明を空間に配置して評価する機構である。[W07] HDRP 17.0のSSGI資料には、SSGI/RTGIによるLightmap/Light Probeの置換や、Mixed tracingの制約がある。採用版でのAPV・反射・fallbackとの接続は独立した検証項目にする。[W08] SSRはスクリーンスペースの反射であり、RT反射への切替にも個別設定が必要である。[W09]

### 4.3 影・空気・写真表現

主光は方向と角直径を管理した太陽光。環境光と間接光で暗部を残しつつ読めるようにする。シャドウマップを基盤とし、近接する駒と盤には控えめなContact Shadowsを比較する。AOは接触の補助で、太い黒縁や二重の暗さを作らない。影のbiasは実際の駒の薄さとセルの実寸で検査する。

Volumetric Lightingは薄い空気感のために限定する。晴天の広場に一律の強い光柱を置かない。噴水は水面、落下する水のメッシュ／粒子、飛沫へ分け、初期は流体シミュレーションを要求しない。カースティクスを足す場合は光学近似であることを記録する。

内部のHDRレンダリングとHDRディスプレイ出力を区別する。初期評価はSDR表示へ固定し、固定露出、ホワイトバランス、ACES系とNeutral系のトーンマッピングを比較する。発光エフェクトのたびに自動露出で盤が暗くならない構成を推奨する。

DOFは映画カットで背景分離に使い、幾何の検査・操作中は停止する。4D断面が変わる間のMotion Blurは、妥当なmotion vectorが確認されるまで使わない。色収差、フィルム粒子、レンズ汚れを写実性の必須条件にしない。

透明レイヤーは必要な場所だけ使う。全面の透明板を多数重ねず、意味のあるセルの断面・稜線と、装飾的な発光線を別アセット・別切替にする。

### 5.1 カメラ案

Scene 01は盤を主役とする斜め上の全景と、木肌が読める穏やかな寄り。Scene 02は実際の駒の高さを示す小さな上昇。Scene 03の幾何確認ではカメラを固定し、断面の変化だけを見せる。Scene 04は開始構図に戻す。Scene 05は実際に許可された移動方向を追い、結果の駒と盤を見せて終える。

焦点距離35〜55mm相当を作業用候補とするが、画像から実際の焦点距離を復元できたとは扱わない。カメラの動きは断面の回転に混ぜない。ユーザーが検査・操作モードへ入った後に、勝手に映画再生へ戻らない。

### 5.2 逃走可能マスと軌跡

一様なセル間隔ℓと盤座標の原点oを使う場合、4Dのセル体積を `C_q=o+ℓ(q+[-1/2,1/2]^4)` と定義できる。表示するのは `H∩C_q` の多面体と稜線であり、元の4D格子の辺を3Dへ投影したものではない。

候補の意味はRuleCoreの合法手集合から受け取り、その候補セルの断面を描く。候補セルが見えなくても合法手集合から削除せず、必要時の別注釈で扱う。セルが交差していても、その中の小さな駒ソリッドが交差しているとは限らない。駒の実体可視性は別に計算する。

移動は元の4D経路γ(t)と駒ソリッドの各時刻の交差として表示する。過去の経路を残すなら、実体とは別の履歴である。経路に太さを持たせた4Dチューブの断面を表示する方式と、説明用に3D投影した軌跡を表示する方式も区別し、後者を厳密断面と呼ばない。

## 6. Scene 03：真の4D回転の詳細設計

本節は本プロジェクトの数学的導出である。特定の「4D Minecraft」実装と同じ内部アルゴリズムであるという主張ではない。

### 6.1 座標系と超平面

ルール座標は `(f,u,v,w)` とし、fを前方軸、表示上のvを高さとして選ぶ。表示の都合でvを上にしても、非前方軸のルール上の対称性は変えない。N=2では高さは造形用の寸法であり、第3の着手座標ではない。

盤中心を `P ∈ R^4`、観察超平面を

\[
H_t=\{P+B_t\xi\mid\xi\in\mathbb R^3\},\quad
B_t\in\mathbb R^{4\times3},\quad B_t^TB_t=I_3
\]

とする。単位法線nについて `Bᵀn=0`、`||n||=1`。駒iの4DソリッドをS_i(t)とすると、描くメッシュは

\[
\partial_{\mathbb R^3}\{\xi\mid P+B_t\xi\in S_i(t)\}
\]

である。**まず交差集合を求め、その3D境界を描く。任意の4D頂点を `Bᵀ(X−P)` で投影するだけでは断面にならない。**

### 6.2 回転

座標平面(i,j)の回転は

\[
x'_i=\cos\theta\,x_i-\sin\theta\,x_j,\qquad
x'_j=\sin\theta\,x_i+\cos\theta\,x_j.
\]

盤中心を固定し、`B'=RB`、`n'=Rn` とする。ゲーム内のqや駒の4D配置は、この操作では変更しない。4Dの回転行列はSO(4)の要素として扱い、3D Quaternion一つで全4D回転を表したとはしない。

4Dの回転には6つの座標平面がある。一方、原点を通る超平面の向きは法線による3自由度であり、残りは断面内部の3D基底の向きと関係する。超平面の向き、内部基底、3Dカメラの向きを区別する。保存するのは角度だけでなく最終の直交フレームと回転規約である。

### 6.3 盤中心と歩を見せたまま、w移動を見せられる構成

初期断面を `H0: w=P_w=0` とする。対象の歩の中心p0もw=0にあるとする。

元の水平平面内から単位方向aを選び、

\[
a\cdot(p_0-P)=0,\qquad a\cdot e_v=0,\qquad a\cdot e_w=0
\]

を満たすようにする。これは水平面内で、盤中心から歩へ向かう方向と直交するaを選ぶ方法である。歩がScene 02で上へ移動していても、aには垂直成分がないので同じ条件を使える。

次にa–w平面内で断面を回転させ、

\[
n_\theta=\cos\theta\,e_w-\sin\theta\,a
\]

とする。このときp0とPは回転の全過程でHθに残る。

90度では

\[
H_{90}=\{X\mid a\cdot(X-P)=0\}
\]

となり、**第4軸e_wそのものが断面内に入る**。したがって停止後に

\[
p(s)=p_0+\Delta w(s)e_w
\]

と移動しても、歩の中心を同じ固定断面の中で追える。観察断面を駒に追従させる必要はない。

この90度案は数学的に構成しやすい候補であり、画像・形状・演出上の最終推奨角の確定ではない。特に単純押し出し駒は90度で通常の駒形状や漢字の見え方を維持しないことがある。斜めの停止角も比較する。

一般の角度では、w移動による中心の符号付き距離の変化は `Δd = Δw cosθ`。したがって、停止時に見えていても移動途中で断面から外れることがある。停止角だけでなく移動全区間で交差を調べる。

### 6.4 「大部分の駒が消える」条件

凸な駒S_iについて

\[
d_{\min}=\min_{X\in S_i}n\cdot(X-P),\quad
 d_{\max}=\max_{X\in S_i}n\cdot(X-P)
\]

を評価する。凸多面体なら頂点で極値を求められる。

\[
S_i\cap H\ne\varnothing\iff d_{\min}\le0\le d_{\max}.
\]

非凸体を複数凸体で表す場合は各成分に判定する。全成分の頂点をまとめた最小・最大だけでは、間の空白で誤って交差ありと判定し得る。

対象の歩を通る断面が、同じ列や近い位置の別の駒を通ることもある。90度では駒の空間的な幅と配置が大きく効き、w方向の厚みだけを小さくしても解決しない。**正式な配置、aの方向、形状寸法から実際の可視集合を算出する。人数合わせのhideフラグは作らない。**

「大部分」の数値基準は人間が選ぶ。自動レポートは可視枚数・駒ID・接触状態を示すだけにする。

### 6.5 順序の契約

| 順序 | 変更するもの | 変更しないもの |
|---|---|---|
| 1 | 観察断面を盤中心の周りに回転 | 駒のゲーム内4D座標、手番 |
| 2 | 目的の角度で断面停止 | 任意の駒消去はしない |
| 3 | 受理済みの歩のw移動を4Dで補間して表示 | 断面を後追いで動かさない |
| 4 | 歩の移動完了後、CPUターンの処理へ進む | CPUへ可視駒だけを渡さない |
| 5 | 観察断面をH0へ戻す | 逃げた歩のw座標を戻さない |
| 6 | CPUの着手・表示をシナリオ契約に従って進める | 映画の都合で非合法手を成立させない |

CPUの思考開始と、着手結果を画面に出す時刻を区別する。復帰中にCPU手を描くか、復帰後まで待つかは未決定。ルール上の手番確定タイミングは既存エンジン契約に合わせる。

元の断面へ戻ったとき、軸整列した押し出し駒で `|p_w-P_w|>h_w` なら駒は不交差となる。これは不透明度のアニメーションではない。

### 6.6 数値を置いた構成例（正式局面ではない）

幾何の意味を説明するため、単位をセル長とし、

\[
P=(0,0,0,0),\qquad p_0=(2,0,1,0)
\]

と置く。座標順は(f,u,v,w)。歩は盤中心から前方へ2、高さ方向へ1、w=0にあるという例で、実際の配置・合法手・アセット寸法を承認する値ではない。

回転方向をu–w平面として、

\[
B_\theta=[e_f,\ \cos\theta\,e_u+\sin\theta\,e_w,\ e_v],\qquad
n_\theta=\cos\theta\,e_w-\sin\theta\,e_u
\]

とすれば、Pとp0は全角度で断面上にある。90度ではH90がu=0になり、断面内座標は(f,w,v)となる。歩がw=0からw=1へ進むと、表示上は(2,0,1)から(2,1,1)へ動く。これは観察する断面内の第2基底がuからwへ入れ替わった結果であり、元のu座標を移動したことにはならない。

別の駒がu=2を中心とし、その全形状が1.7≤u≤2.3に収まるなら、u=0とは交差しない。一方、同じu=0付近の駒は残り得る。

押し出し歩のw半厚を仮に0.2とすると、w=1へ移動後の全形状は0.8≤w≤1.2にある。そのまま元のH0:w=0へ戻れば、実体は空集合になる。この例は式から導かれる条件であり、実機試験や多数の駒の消失を確認した結果ではない。

## 7. 4D形状と断面メッシュ

### 7.1 推奨する形状

通常の駒を、面取りした閉じた凸な3DソリッドK3として作り、

\[
S=K_3\times[-h_w,h_w]
\]

へ拡張する。盤も有限の4Dソリッドとする。盤のw半幅と駒のw半厚は別パラメーターであり、ゲーム開始／プリセット確定時に固定する。wの一マスの物理長も明示する。

盤のw幅は、停止断面で見せる範囲や予定された歩のw経路を支えられるように設定する案。ただし大きすぎれば回転中に卓からはみ出す。形状を角度ごとに伸縮して帳尻を合わせない。

閉じた3Dメッシュの外殻だけをw方向へ引き伸ばしても、必要な4D境界のすべてを表したことにはならない。

\[
\partial(K_3\times I)=(\partial K_3\times I)\cup(K_3\times\partial I).
\]

両端に3D体積のセルが必要である。4D境界を表す主な要素は3Dセルであり、普通の3Dメッシュの三角形とは次元が異なる。

### 7.2 半空間を3Dへ制限する方法

世界4D座標で

\[
S=\{X\mid a_j^TX\le b_j,\ j=1,\ldots,m\}
\]

と表す。観察超平面 `X=P+Bξ` を代入すると、

\[
(B^Ta_j)^T\xi\le b_j-a_j^TP
\]

になり、通常の3D凸多面体を定義する不等式が得られる。これをクリップして頂点・面を作り、各面を三角形化する。

元の外周・面取り面・w端面のIDを維持することで、法線、木目、文字材、断面材の割当を追跡できる。三つの制約面の組合せから候補頂点を作る方法は独立した検算用にも使えるが、制約数増加時の計算量を考慮する。

`||Bᵀa_j||` がほぼ0の制約を無理に正規化しない。右辺に応じて常に満たす、全体を排除する、共面となる場合へ分類する。数値許容誤差は単位と形状スケールに応じて定義し、観察超平面を厚いスラブに変更するためには使わない。

### 7.3 CPU / GPU / 陰関数の比較

| 方法 | 正しさの表し方 | 利点 | 難所 | 扱い |
|---|---|---|---|---|
| CPU凸半空間交差 | 定義した多面体の断面を求める | 検証しやすい。通常のMeshRendererに接続可能 | 面の整列、共面、アップロード | **初期推奨** |
| 4D境界セルの四面体分割 | 3D境界セルと超平面の交差 | 複雑な境界へ一般化しやすい | 端セル、重複面、内部面、共面退化 | 汎用化候補 |
| GPU Compute | 同じセルや制約の交差を並列化 | 大量形状で転送を減らせる可能性 | バッファ上限、同期、全描画パス、RT登録 | 計測後に判断 |
| 4D陰関数／SDF | H上の点で4D場を評価 | 滑らかな固定形状や材質場と相性がよい | サンプリング誤差、レイ収束、影・深度・履歴統合 | 小さな比較試験 |
| 元メッシュの単純投影 | 交差を計算しない | 容易 | 要求を満たさない | 不採用 |
| 元3Dメッシュのfragment clipだけ | 元の面の一部を消す | 容易 | 新しい切断面や4D形状が生まれない | 単独方式として不採用 |

4D境界の四面体はR4に埋め込まれた3-simplexであり、一般位置ではHとの交差が三角形または四角形になる。四面体全体がH上にある退化ケースでは3D体積が交差しており、通常の三角形テーブルだけでは処理できない。共面領域の合成と内部面除去が必要。4D内部を埋める4-simplexは5頂点であり、これと混同しない。

陰関数Φ4の場合、3Dレイ `ξ=o+td` に対し `Φ4(P+B(o+td))` を評価すれば、真の断面に対するレイ計算になる。ただし数値探索の誤差と、描画パイプラインへの統合が別途必要である。

### 7.4 データ契約

| データ | 必須内容 |
|---|---|
| Shape4D | 形状ID・版、凸成分、4D制約面または境界セル、面ID、材質ID、局所材質座標 |
| Instance4D | 駒ID、姿勢、単位、形状版、材質シード、局面版 |
| SliceState | 盤中心P、B、n、回転規約、版、数値許容方針 |
| SectionMesh | 3D位置、局所4D位置、法線、必要な接線、面ID、由来ID、indices、bounds |
| SectionStatus | Empty、低次元接触、3D断面、数値不確定、容量超過等 |
| HistoryState | 前フレームの由来、対応可能性、履歴を使えるかどうか |

Unityの左右・軸順・法線の向き・単位変換はadapter内で統一し、ピッキングにも同じ逆写像を使う。駒IDをメッシュの配列順から復元しない。

### 7.5 退化と不連続

断面は常に滑らかに小さくなって消えるとは限らない。押し出し形 `K3×[-h,h]` をw一定で切ると、端の `w=h` においても断面はK3全体であり、その直後に空集合となる。接触が必ずゼロ体積になるわけではない。

滑らかな消失が必要なら、初めからw端を面取り・丸めた別の固定4D形状を比較する。これは正当な形状設計の変更だが、単純な押し出し形とは別物なので形状版と承認を更新する。消失直前だけ透明化して幾何の問題を隠さない。

## 8. 木製駒の外観と断面の両立

### 8.1 形状の共通化

**通常時の美しい駒と、回転時の断面用駒を別の無関係なモデルにしない。** 通常表示も同じSのH0断面から得る。形状の面取りは元の4Dソリッドに含める。光学的な細部だけをnormal・roughnessへ分ける。

高解像度の複雑な彫刻を全部真の4D形状へ入れると、非凸化・面数・断面トポロジーが増える。初期は「シルエットと面取りは幾何、微細な木肌と浅い文字凹凸はシェーディング近似」と定義する。深い彫刻まで実際に切る版は後段とする。

### 8.2 固定された材質場

物体局所の4D座標rに対し、

\[
M_4(r)=(\mathrm{baseColor},\mathrm{roughness},\mathrm{grain},\mathrm{finish},\mathrm{glyph},\ldots)
\]

を定義する。断面頂点は、生成時に元の物体局所4D座標を持つ。フラグメントはその位置と元の面IDから材質を参照する。

最初の拡張案は `M4(f,u,v,w)=M3(f,u,v)`、すなわちw方向に同じ木材構造を押し出すもの。これは観測された「実物の4D木材」の物性ではなく、プロジェクトで定義する材質規約である。必要に応じて低周波のw変化を加えるが、回転角に応じて別の木目へ交換しない。

既存の外面には校正した木材テクスチャと仕上げを使い、内部的な表現が必要な場所は連続的な木目場と対応させる。断面の新しい3D座標へ毎回UVを貼り直す方法では、木目が物体に対して滑る可能性があるため採用しない。3D triplanarだけでは、元の4D材質構造の定義の代替にならない。

### 8.3 法線・接線

4D境界面の法線をN4とすると、一般位置における断面表面法線は

\[
N_3=\frac{B^TN_4}{\|B^TN_4\|}.
\]

陰関数なら `∇ξ Φ4(P+Bξ)=Bᵀ∇X Φ4`。分母が小さい場合は退化処理へ回す。通常の3D法線を回転して使い回すだけでは不十分である。

局所材質座標の微分から接線方向を求め、grainの方向とnormal detailを整合させる。接線が退化した領域では、幾何法線優先の安定したfallbackにする。新しくできた稜線を見栄えのために丸く塗りつぶし、実際の形状と違う輪郭にはしない。

### 8.4 漢字と仕上げ

文字は元の駒の上面に対応する4D境界上のマスクとして定義する。そのマスクも断面に制限する。切れて読めなくなる、細長くなる、見えなくなることは許容する。特に90度の単純押し出し形では、文字の一部がw方向に伸びた帯として見える場合がある。

**毎回きれいな「歩」を新しい面の中央へ貼り直すのは、固定された4D材質の断面ではない。** 読みやすさが必要なら、選択時だけの別情報表示または明示した注釈を使う。起動時の常時UIにはしない。

すべての生成面を「新しく鋸で切った面」と解釈するのも避ける。どの4D境界が塗装・仕上げ済みか、w端面をどう扱うかをShape/Materialの定義で決める。観察断面の回転は物体を物理的に切断する出来事ではない。

### 8.5 高級木材表現の段階

基準は通常のPBR＋適切な木目・粗さ・仕上げ。さらに必要なら、繊維方向に依存する輝きの拡張を比較する。仕上げ木材の反射には表面下の繊維による特徴があり、単純な表面異方性だけでは説明しきれないことが原著研究で示されている。[W10]

ただし、その研究モデルを導入する前に、標準Litで作った駒を実際のショットで人間が確認する。高度なBRDFの名称だけで品質向上を見込まず、GPUコスト、RT版との一致、Quest用の代替を評価する。

### 8.6 通常形を見せやすい「固定された4D形状」の比較候補

単純なw押し出しだけが正しい4D形状ではない。外観を改善するために、観察中に形を入れ替えるのではなく、初めから別の固定4D形状を定義することはできる。

| 形状 | 長所 | 注意点 | 状態 |
|---|---|---|---|
| A：K3×Iの単純押し出し | 最も検証しやすい。一般の凸K3に適用 | 90度で通常の駒とは違う形・文字になり得る。平らなw端で急に消える場合がある | 初期の数学的基準案 |
| B：w端部を面取りした4D凸体 | 境界付近の断面縮小を幾何として設計できる | 全角度で滑らかな消失になる保証ではない。形状版が変わる | 比較候補 |
| C：uとwに同じ駒幅形状を持つ4D凸体 | 特定の0度・90度断面で通常の駒形状を得られる | 対称な通常形と回転方向に条件がある。中間角では変形し、漢字は別問題 | 外観重視の比較候補 |

Cの具体的な構成を示す。左右方向uについて対称な通常駒を

\[
K_3=\{(f,u,v)\mid (f,v)\in D,\ |u|\le\rho(f,v)\},\qquad\rho\ge0
\]

と表せるとき、

\[
S_{\mathrm{sym}}=\{(f,u,v,w)\mid(f,v)\in D,\ |u|\le\rho(f,v),\ |w|\le\rho(f,v)\}
\]

を定義する。w=0の中心断面は元のK3であり、u=0の中心断面も、uをwへ読み替えた同じ駒形状になる。ρを複数の一次式の最小、Dを凸な多角形領域で表せる場合は、有限の半空間による凸体として扱えるため、CPUの半空間交差方式に接続できる。

例えば局所u–w平面の中間角では、対応する断面内の幅座標sに対し、|s|≤ρ/max(|cosθ|,|sinθ|)となる。45度で幅が広がるのも定義した形状の断面であり、通常メッシュを角度ごとに差し替える処理ではない。

この構成を§6.6のu=0の歩へ使えば、停止後のw移動を、普通の駒に近いシルエットのまま見せられる。異なる配置・任意の回転方向で同じ性質が成り立つとは断定しない。陣営・駒の姿勢も含めて適用条件を検証する。

**形が一致しても、漢字や木目まで自動的に同じになるわけではない。** 文字・仕上げは固定されたM4として別途定義し、w=0とu=0の両方で読みやすくしたい場合は、その両断面に整合する4D材質設計を比較する。カメラ角度に応じて文字を貼り直す処理は別の補助表示であり、材質場の断面に混ぜない。

Cを承認済み形状にせず、Aとの小さな外観・幾何比較へ留める。正式なw厚み、盤のw幅、着手可能領域はこの式だけでは確定しない。

## 9. 動的トポロジー、シェーダー、処理負荷

### 9.1 初期CPU方式

形状ごとに再利用バッファを持ち、必要なインスタンスだけを切る。観察断面も物体姿勢も変わらない場合は再利用する。CPU参照計算は倍精度を候補とし、実時間経路のfloat版と差分比較する。

UnityのMeshData APIはJobsからの作成・更新に利用できる。参照数学とUnity adapterの依存を分け、毎フレームの大量のMesh生成・破棄やGC、MeshColliderの再構築を避ける。[W11]

盤の全マスをGameObject化しない。局面はスパースな駒集合、格子は手続き的な線、候補マスは必要なものだけの断面として作る。

### 9.2 GPUへの移行条件

CPU断面生成が実測で予算を超え、形状の簡略化や更新抑制では解決しない場合に移行する案。

候補分類 → 出力面数計算 → prefix sum → 頂点・indices出力 → 間接描画、という段階を比較する。GPU→CPUの毎フレームreadbackを前提にしない。容量不足はログと診断状態にし、末尾の駒を黙って捨てない。

画面外判定と、幾何学的な断面不交差を区別する。メインカメラから見えないだけの断面物体も、影や反射に必要なことがある。色パス用の可視性だけで全パスを間引かない。

GPUで生成した任意の間接描画ジオメトリが、そのままHDRPのRT加速構造へ登録されるとは仮定しない。対応経路を試験し、必要ならCPUの通常メッシュ経路を維持する。

### 9.3 全パスの一致

Color / GBuffer / Forward / Depth / Normal / Shadow / Motion Vector / Reflection / RTの対象形状を同じSection版へ揃える。HDRPには動的ジオメトリのRT更新設定があるが、トポロジー更新時のコストと適用条件は実機確認が必要。[W12]

### 9.4 TAA・DLSS・ブラー

HDRPのTAAは履歴とmotion vectorを利用し、残像が発生する場合がある。[W03][W13] DLSSも利用候補だが、導入すれば動的トポロジーの対応関係が自動的に正しくなるわけではない。[W14]

頂点配列の同じ番号を前フレームの同じ点とみなさない。元の4D辺IDや制約面の組合せなどから、前断面に存在した対応点を再計算する。現在の4D点を前のBへ投影するだけでは、その点が前の超平面上に存在した保証がない。

この対応は幾何特徴の追跡規約であり、切断で新たに露出した材質点が前フレームに存在したことを保証しない。面内ピクセルの再投影には可視性・深度・材質の整合確認も必要である。

新生面・消失面は履歴対応なしとして扱う。対応するhistory rejection等を採用版へ実装できるかは技術検証事項であり、標準Litだけで解決済みとはしない。うまくいかなければ非時間型AAを維持する。毎フレーム画面全体の履歴をリセットして品質問題を隠さない。

## 11. 性能目標と予算

### 11.1 目標

| 用途 | 提案する出力 | 判定 |
|---|---|---|
| 最初の幾何・質感検証 | 1920×1080、実描画60fps | ネイティブ基準。RTなしでも可 |
| PC Showcase本目標 | 2560×1440、実描画60fps | 未測定。品質プロファイル・内部解像度も記録 |
| フォールバック | 1920×1080、60fps | 幾何を偽装せず、重い光学効果から調整 |
| 高解像度比較・収録 | 4K/30fps候補、または静止収束画像 | 通常プレイ目標と別扱い |

フレーム生成された表示枚数と、実際の断面更新・レンダリング枚数を分ける。目標判定ではFrame Generationを使わない。60fpsの総時間枠は約16.67ms。CPUとGPUは並行するため、CPU時間とGPU時間を単純に加算せず待ち時間を含むクリティカルパスを調べる。

### 11.2 初期の工程別予算案

以下は測定値や達成予測ではなく、設計時の作業配分である。PBRと駒の描画等は同じGPUパスへ統合されるため、実測では重複計上しない。

| 工程 | 主負荷 | 目標枠の案 | 測定対象 |
|---|---|---:|---|
| 屋外背景の基礎描画 | GPU/描画CPU | GPU 2.2ms | 遠近LOD、葉のoverdraw、描画数 |
| PBR材質の追加費用 | GPU | GPU 1.2ms | shader命令、texture帯域、近接材質 |
| 影 | GPU | GPU 2.4ms | cascade、接触影、caster数 |
| GI・反射 | GPU/VRAM | GPU 3.0ms | GI構成、SSR/RT、加速構造費用 |
| ポスト処理 | GPU/VRAM | GPU 1.8ms | AA、DOF、Bloom、履歴 |
| 3D/4D格子・補助表示 | GPU/CPU | GPU 0.5ms | 透明重なり、線の細かさ |
| 4D交差計算 | 初期CPU | CPU 1.0ms | 候補駒数、制約数、退化 |
| 動的メッシュ構築・転送 | CPU/GPU | CPU 1.0ms、GPU 0.4ms | 転送量、同期、バッファ確保 |
| 駒・盤の基礎描画 | GPU/CPU | GPU 0.6ms | 断面面数、バッチ、depth |
| その他 | CPU/GPU | GPU 1.1ms | 合成、描画管理、未分類 |

GPU配分合計は13.2msで、残り約3.47msを変動・未分類への余裕とする。CPUクリティカルパスは10ms以内を作業目標にし、CPU思考を描画待ちへ直結させない。RTやCompute導入時はこの配分を作り直す。元の値に負荷を積み上げて予算達成と呼ばない。

### 11.3 VRAM

16GBの参考GPUに対して、初期はアプリの常駐量を概ね10〜12GiB以下へ収める作業目標を置き、OS・表示系・一時バッファへの余裕を測る。

概算配分候補は、texture 5〜6GiB、lightmap/probe 1〜1.5GiB、mesh 0.5〜1GiB、render target/history 1〜1.5GiB、断面作業buffer 0.25〜0.5GiB、その他とRT加速構造は残りを実測する。ファイル容量、GPU予約量、実常駐量を混同しない。上限値同士を無条件に足して採用可能とは判断しない。

### 11.4 測定計画

固定された着手列・カメラ・断面角の入力を再生し、同じ条件で比較する。通常盤、最も多くの駒が交差する角度、共面付近、消失直後、Scene 05のVFX最大時を別区間として測る。

各区間30〜60秒を3回程度、shader/textureのwarm-up前後を分離し、別に10〜15分の連続動作で熱・クロック・常駐量を見る案。Editorの計測とStandalone Playerの結果を区別し、Development計測のオーバーヘッドも記録する。Unity ProfilerはCPU・描画等の分析基盤として使用できる。[W18]

保存するもの：中央値、p95/p99、最悪フレーム、CPU main/render/worker、GC allocation、GPUパス別時間、buffer転送、同期待ち、triangle/draw数、VRAM常駐、RT更新時間、内部/出力解像度、AA、ドライバー、電源条件、品質設定。

平均60fpsだけでは受け入れない。目立つカクつき、漢字の崩れ、材質の泳ぎ、消えた駒の残像を動画で確認する。美しさの最終判定は人間が行う。

## 12. PCとQuest 3の技術分離

| 項目 | PC Showcase | Quest単体版 |
|---|---|---|
| 描画基盤 | HDRP、DX12候補 | URP、XRに適合するAPI |
| 幾何の意味 | 同じ4D形状・超平面の契約 | 同じ。擬似3Dへ置き換えない |
| メッシュ | 高い面取り品質、必要な細部 | 誤差を定義したLOD。形状差を隠さない |
| 材質 | 高解像度、仕上げ、任意の高度BRDF | 少ないtexture参照、単純化した木材近似 |
| GI/反射 | ベイク基準＋任意のSSR/RT | ベイクと限定プローブ中心 |
| 影 | 近景品質重視 | 距離・caster・解像度を限定 |
| AA | 基準SMAA、履歴を検証後TAA/DLSS | Forward＋MSAAを候補 |
| VFX | 画面構図に合わせた控えめな演出 | 透明overdrawを減らす |
| カメラ | 映画的な自由移動 | 頭部姿勢を尊重。視点を強制移動しない |
| 目標 | 1440p/60fps候補 | 72Hzを初期候補、90Hzは後続比較 |

Metaの現行資料では、Unity 6000.3以降の組込みURPにQuest向けForward+最適化が含まれる。ただし少数光源ではForwardが適する場合があり、両者を比較する。[W19] 単体VRでのタイルGPU・帯域を踏まえた設定はPCとは分ける。[W20]

72Hzは約13.89ms、90Hzは約11.11msの枠。HMDの合成・再投影された表示を、アプリの実描画の達成として数えない。[W21] PCの1440pをそのまま片眼の解像度目標へ置き換えず、実際のeye bufferとrender scaleを記録する。

共有するのはRuleCore、シナリオ形式、形状定義、断面数学、元材質データ。HDRP/URPのshader、材質変換、照明ベイク、LOD、VFX、カメラ制御は別。PCVRでQuestをPCへ接続する構成は、Quest単体版とも別の性能・XR検証枠とする。

## 13. 技術的難所と対策

| リスク | 失敗の例 | 先に確認すること |
|---|---|---|
| 回転角と局面の不一致 | 目的の歩が消える、他駒が大量に残る | 全駒の交差を解析して角度と形状を選ぶ |
| 押し出し形の見た目 | 90度で板状・棒状、文字が帯になる | 単独の歩で斜角と90度を比較 |
| 共面・接触 | 穴、重複面、反転、突然のNaN | 端面一致を含む退化試験 |
| 材質座標 | 木目が滑る、面境界で模様が途切れる | 局所4D位置と面IDで検査 |
| 時間方向の履歴 | 消えた駒が残る、文字が引きずる | 非時間型基準との差分と履歴無効化 |
| RT不整合 | 色では切断済み、反射は元の駒 | RTASの可視化と動的更新試験 |
| 静的GIの焼込み | 逃げた駒の影が卓に残る | 動的物体をベイクへ固定しない |
| 透明物の重なり | 格子や水で帯域を消費、順序破綻 | 格子密度とtransparent overdraw |
| 映画とルールの混同 | 王を取る演出で勝ちを決める | ルールイベントと装飾イベントの分離 |
| 背景制作が先行 | 広場だけ綺麗で断面が未成立 | 木製駒単体と幾何を最初に並行検証 |
| 素材の権利 | paid素材の元データを公開 | 調達・公開・AI入力可否を個別確認 |
| Questへの早すぎる最適化 | PCの主役まで簡略化 | 描画側を分離し、共通幾何を維持 |

### 14.2 システムの検証観点
